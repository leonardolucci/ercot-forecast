# REPOSITORY STRUCTURE

> **Stable** reference file. It describes the target tree, the derivation flow
> and the criteria used to decide where each new file goes. It changes rarely:
> only when a folder is added or removed.
>
> The actual state of what exists on disk today is in `STATE.md`, not here.

---

## 1. Target tree

```
ercot-forecast/
│
├── README.md              source · what this is and how to run it
├── CLAUDE.md              source · hard rules of the project
├── pyproject.toml         source · description of the environment
├── .gitignore             source · what NEVER enters Git
├── .env.example           source · the SHAPE of the secrets, never the values
│
├── config/                source · run parameters (dates, paths, thresholds)
│
├── src/
│   └── ercot_forecast/    source · EVERYTHING that gets imported
│       ├── __init__.py
│       ├── ingest/
│       ├── features/
│       ├── models/
│       ├── evaluation/
│       └── decision/
│
├── scripts/               source · executable entry points
├── tests/                 source · mirror of src/ercot_forecast/
├── notebooks/             source · laboratory, dead leaf of the graph
│
├── data/                  DERIVED · Git-ignored · created by the code
│   ├── raw/                 immutable, append-only, exactly as it arrived
│   ├── interim/             intermediates of a two-step transformation
│   └── processed/           canonical tables ready for features
│
├── artifacts/             DERIVED · Git-ignored · created by the code
│   ├── models/              serialised trained models
│   └── figures/             figures generated by a run
│
└── docs/                  source · prose written by a human
    ├── ROADMAP.md
    ├── STATE.md
    ├── STRUCTURE.md
    └── IDEAS.md
```

**Deliberately absent:** `utils/`, `helpers/`, `api/`, `dashboard/`, `deploy/`.
What gets created is what has a defined role, not what might turn out to be
useful.

**`data/` and `artifacts/` are not created by hand.** The ingestion code creates
them. Derived rule: *any code that writes to `data/` or `artifacts/` creates the
directory if it does not exist.*

## 2. Derivation flow

```
   outside world (ERCOT, weather forecasts)
              │
              │   ← ONLY scripts/ touches the outside world
              ▼
        data/raw/  ──────────────► immutable. never edited in place
              │
              ▼
     data/processed/
              │
              ▼
   ingest → features → models → evaluation → decision
              │            (imports point rightward only)
              ▼
      artifacts/ + prose in docs/
```

---

## 3. Decision axes — where a new file goes

Four independent questions. The position on all four determines the destination.

| Axis | Question | Operational test |
|---|---|---|
| **A** — source vs. derived | if I delete it, do I regenerate it by running something from the repo? | yes → derived (`data/`, `artifacts/`, ignored) · no → source (version-controlled) |
| **B** — library vs. entry point | if I import it and do nothing else, does anything observable happen in the world? | no → `src/` · yes (network, disk, writes) → `scripts/` |
| **C** — of the project vs. of the machine | does it have to be identical for anyone who clones? | yes → version-controlled · no (venv, `.env`, absolute paths) → ignored |
| **D** — logic vs. parameter | is there more than one legitimate value I might want to run, without the code changing behaviour? | yes → `config/` · no → `src/` |

**Complementary test for axis B:** can I call it with made-up data and compare
the result against an expected value? If yes, it is library.

**Edge case for axis A:** `data/raw/` looks derived (a script produced it) but is
unrecoverable (if ERCOT withdraws the endpoint, it cannot be regenerated). It
weighs as derived, it is worth as much as source. Hence open problem 1 in
`STATE.md`.

**Edge case for axis D:** a schema of expected columns is NOT a parameter. There
is exactly one valid value at a time. It is a contract, it goes in `src/`.

## 4. Invariants this structure makes verifiable

1. **Nothing derived enters version control.** Enforced by `.gitignore`.
2. **Imports point in a single direction:** `ingest → features → models →
   evaluation → decision`. If `ingest/` needs to import from `models/`, an import
   is not missing: a function is in the wrong place.
3. **No feature reads a record whose `available_at` is later than the moment of
   prediction.** Enforced by a CI test (Phase 2). It is only auditable because
   the logic is importable without side effects — hence axis B.

**Root criterion:** the root holds only what a tool reads by convention
(`pyproject.toml`, `.gitignore`, `CLAUDE.md`) or what a stranger needs in the
first 30 seconds (`README.md`). Everything else goes one level down.

**Quality metric:** how short the statement of the invariants stays. If
`.gitignore` needs thirty exceptions, the structure is wrong.
